# Fault-Tolerant Payments Ledger

A payments-systems project focused on **correctness under retries, crashes, and concurrent transfers**.

> **Status:** active build. Performance figures below are engineering targets until reproduced by the benchmark suite.

## Goals

- Double-entry ledger where every committed transfer balances to zero
- Idempotent transfer API to prevent duplicate charges after client/network retries
- PostgreSQL transactions with deterministic account-lock ordering
- Transactional outbox for reliable Kafka/Redpanda event publication
- Seeded fault-injection simulator for repeatable correctness testing
- Load tests for throughput and p99 latency

## Target Resume Metrics

- 0 balance errors across 50,000+ seeded fault-injection tests
- 3,200 transfers/sec at <35 ms p99
- No duplicate idempotency applications
- No account-limit breaches

These numbers are **targets, not claimed results**, until generated by this repository's tests.

## Architecture

```text
Client
  |
  v
Go HTTP API
  |
  +---- idempotency_keys
  |
  +---- accounts / transfers / ledger_entries
  |
  +---- outbox_events ----> publisher ----> Redpanda/Kafka
              |
              +---- same PostgreSQL transaction
```

A transfer is committed atomically with:
1. the transfer record,
2. equal-and-opposite ledger entries,
3. the idempotency result, and
4. the outbox event.

## Core Invariants

```text
1. SUM(ledger_entries.amount) for every transfer == 0
2. An idempotency key is applied at most once
3. A transfer cannot violate configured account limits
```

## Why This Project

Most student payment apps demonstrate CRUD. This project is intentionally about the harder part: preserving financial invariants when requests are retried, processes crash, and multiple transfers race for the same accounts.
